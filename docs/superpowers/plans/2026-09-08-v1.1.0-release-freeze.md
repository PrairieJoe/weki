# Weki v1.1.0 Release Freeze Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Freeze the current Weki implementation as v1.1.0, synchronize release documentation and installer metadata, verify the shipped artifacts, then update GitHub and publish the Windows installer.

**Architecture:** Treat the current working tree as the release candidate. Verify functional changes first, then finalize release notes and reproducible package metadata from the actual build output. Commit the release, safely resolve the existing tag, push, and publish verified assets.

**Tech Stack:** Node.js 22+, npm, Node test runner, Vite, Electron Builder/NSIS, Git, GitHub CLI or web release flow.

**Spec:** Active user request: freeze current project state, clean remaining v1.1.0 artifacts and documents, rewrite release notes, update GitHub, and distribute the v1.1.0 installer.

## Global Constraints

- Preserve the user's existing working-tree changes; do not reset or discard them.
- Keep version identifiers, release notes, checksums, update metadata, tag, and installer filename aligned on `1.1.0`.
- Never force-push or overwrite an existing tag without explicit approval.
- Do not publish until tests, production build, packaging, and checksum verification have fresh passing evidence.
- Exclude temporary unpacked installer output and local runtime data from the repository release commit.
- Use `2026-09-08` for the release date unless the actual publish date changes before finalization.
